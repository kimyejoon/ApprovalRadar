> **작성일:** 2026-05-17  
> **시스템 설정값 기준:**
> - `PAGE_SIZE = 1,000` (1회 Request당 최대 조회 건수)
> - `PIVOT_INTERVAL = 5,000` (피벗 희소 색인 간격)
> - `SCRAPER_INTERVAL_MINUTES = 30` (최소 탐색 주기)
> - `API_LIMIT = 1,000` (Key 1개당 일일 최대 호출 수)
> - **추정 총 데이터:** I2859 약 300,000건 (300페이지), I2861 약 250,000건 (250페이지)

## Part 1. API 호출 횟수 시뮬레이션

### 공통 전제 (분석 모델 정의)

```
총 데이터(N)   = 300,000건 (I2859 기준)
페이지 수      = 300페이지 (1페이지 = 1,000건)
피벗 수        = 60개 (300,000 / PIVOT_INTERVAL 5,000)
API 일일 한도  = 1,000회/Key
```

**호출 단계 분류:**

| 단계 | 설명 | 현재 방식 | 개선 후 방식 |
|------|------|-----------|-------------|
| A. Tail 탐색 | 이진탐색으로 꼬리(끝 인덱스) 확정 | `_fetch_page` × ~15회 | 동일 (변경 없음) |
| B. Shift 계산 | 피벗별 밀려난 칸 수 계산 | `_fetch_single` 누적 루프 | `_fetch_page` × 피벗 수 |
| C. 데이터 다운로드 | 신규 삽입 구간 데이터 수집 | `_fetch_page` × ceil(diff/1000) | 동일 (변경 없음) |
| D. 피벗 갱신 | 새 꼬리 구간 피벗 생성 | `_fetch_single` × 새피벗 × 2 | `_fetch_page` × 새피벗 |

> **핵심 포인트:** 현재 방식의 B단계는 내부에서 `current_shift`가 누적 공유되어
> 이론상 총 diff_count 회 호출로 수렴한다. 즉 단건 호출 diff_count 번 vs 페이지 호출 pivot_count 번의 대결이다.

### 시나리오별 API 호출 횟수 비교

#### 🟢 시나리오 1: 정상 운영 — 변동 없음 (diff_count = 0)

| 단계 | 현재 방식 | 개선 후 방식 |
|------|-----------|-------------|
| A. Tail 탐색 (Ping 1회) | **1회** | **1회** |
| B. Shift 계산 | 0회 | 0회 |
| C. 데이터 다운로드 | 0회 | 0회 |
| D. 피벗 갱신 | 0회 | 0회 |
| **합계 (1회 주기)** | **1회** | **1회** |
| **하루 48주기 합계** | **48회** | **48회** |

> 결론: 정상 운영 시 양쪽 모두 하루 약 48회로 극히 효율적. 일일 한도 대비 4.8% 소모.

---

#### 🟡 시나리오 2: 단기 다운 — 소량 누적 (diff_count = 10)

*서버 30분~2시간 장애 시 발생 가능한 수준*

| 단계 | 현재 방식 | 개선 후 방식 |
|------|-----------|-------------|
| A. Tail 탐색 | ~15회 | ~15회 |
| B. Shift 계산 | **단건 10회** (fetch_single, current_shift 누적) | **페이지 60회** (fetch_page × 60 피벗, 각 1회) |
| C. 데이터 다운로드 | 1회 | 1회 |
| D. 피벗 갱신 | ~2회 (새 피벗 1개 × 2) | ~1회 (새 피벗 1개 × 1) |
| **합계** | **28회** | **77회** |

> ⚠️ 예외: diff_count가 매우 작을 때는 오히려 개선 후 방식이 더 많은 호출을 한다.
> 이는 "피벗 60개 × 1 페이지"가 "10번의 단건"보다 많기 때문.
> 그러나 양쪽 모두 1,000회 한도를 절대 초과하지 않으며, 일일 운영 관점에서는 문제없다.

---

#### 🟠 시나리오 3: 주말 다운 — 중간 누적 (diff_count = 500)

*주말 48시간 서버 미가동 시 현실적으로 발생 가능한 수준*

| 단계 | 현재 방식 | 개선 후 방식 |
|------|-----------|-------------|
| A. Tail 탐색 | ~15회 | ~15회 |
| B. Shift 계산 | **단건 500회** ← diff_count에 비례 | **페이지 60회** ← 피벗 수에만 비례 |
| C. 데이터 다운로드 | 1회 (500건 = 1페이지) | 1회 |
| D. 피벗 갱신 | ~10회 (새 피벗 5개 × 2) | ~5회 (새 피벗 5개 × 1) |
| **합계** | **526회** | **81회** |
| **일일 한도(1,000) 대비** | 52.6% — 아슬아슬하게 안전 | **8.1% — 매우 안전** |

> 현재 방식도 1,000회를 넘지는 않지만, 다른 서비스(I2861) 호출과 합산되면 위험하다.
> 하루 동안 I2859 526회 + I2861 526회 = **1,052회 → Key 고갈** 가능성 존재.

#### 🔴 시나리오 4: 장기 다운 — 대량 누적 (diff_count = 2,000)

*1주일 이상 서버 미가동 또는 대형 인허가 이벤트(신규 프랜차이즈 전국 동시 등록) 시 발생 가능*

| 단계 | 현재 방식 | 개선 후 방식 |
|------|-----------|-------------|
| A. Tail 탐색 | ~15회 | ~15회 |
| B. Shift 계산 | **단건 2,000회** ← Key 고갈 직전 | **페이지 120회** (2,000/1,000 = 2페이지 × 60 피벗) |
| C. 데이터 다운로드 | 2회 | 2회 |
| D. 피벗 갱신 | ~30회 (새 피벗 15개 × 2) | ~15회 |
| **합계** | **2,047회** 💀 **KEY 고갈** | **152회** ✅ 안전 |

> 현재 방식: I2859에서만 2,000회 초과 → 즉각 Key 소진, I2861 크롤링 불가, 시스템 정지.
> 개선 후: 양 서비스 합산 304회 → 일일 한도 30.4% 소모, 정상 운영 가능.

#### 💀 시나리오 5: 극한 상황 — 초대량 누적 (diff_count = 10,000+)

*수 개월 미가동 또는 식품안전나라 측 대규모 DB 마이그레이션 발생 시*

| 단계 | 현재 방식 | 개선 후 방식 (Phase 3 Circuit Breaker) |
|------|-----------|---------------------------------------|
| A. Tail 탐색 | ~15회 | ~15회 |
| B. Shift 계산 | **단건 10,000회** 💀 | **즉시 ABORT** (Circuit Breaker 발동) |
| C. 데이터 다운로드 | 진행 불가 (Key 고갈) | 진행하지 않음 (안전하게 중단) |
| D. 피벗 갱신 | 진행 불가 | 진행하지 않음 |
| **합계** | **10,000+회** 💀 영구 크래시 | **15회** ✅ + ALERT SSE 발송 |

### 시뮬레이션 총 요약표

| 시나리오 | diff_count | 현재 방식 호출 수 | 개선 후 호출 수 | 개선율 | 현재 방식 안전 여부 |
|----------|-----------|-----------------|----------------|--------|-------------------|
| 정상 운영 | 0 | 1회/주기 | 1회/주기 | 동일 | ✅ |
| 소량 누적 | 10 | 28회 | 77회 | -175% (소량에서 개선 후가 다소 多) | ✅ |
| 주말 다운 | 500 | 526회 | 81회 | **85% 절감** | ⚠️ 양 서비스 합산 시 위험 |
| 장기 다운 | 2,000 | **2,047회** 💀 | 152회 | **93% 절감** | ❌ Key 고갈 확정 |
| 극한 상황 | 10,000+ | **크래시** 💀 | 15회 + CB 발동 | **99%+ 절감** | ❌ 영구 불능 |

> **결론:** `diff_count ≈ 피벗 수(60) = 60`이 교차점이다. 그 이상의 diff_count에서는 개선 후 방식이 압도적으로 유리하다.

## Part 2. 리팩토링 후 테스트 방침

### 테스트 원칙

1. **관찰 가능성(Observability) 우선:** 모든 테스트는 로그 파일(`server.log`)과 대시보드 UI를 통해 결과를 직접 눈으로 확인할 수 있어야 한다.
2. **실제 API 호출 수 검증 중심:** 이론값과 실측값을 비교하여 알고리즘의 정확성을 증명한다.
3. **회귀(Regression) 방지:** 개선 후 탐지 결과가 기존과 동일한지 확인하여 데이터 누락이 없음을 보장한다.

---

### 테스트 시나리오 1: 정상 운영 — Ping 최적화 검증

**목적:** 변동이 없을 때 API가 정확히 1회만 호출되는지 확인

**실행 방법 (개발자):**
```bash
# 서버 실행 후 로그 실시간 감시
tail -f ApprovalRadar-BE/server.log | grep "\[API 호출\]"
```

**기대 로그 패턴:**
```
[I2859][전략B] Ping: 변동 없음 (XXXXX건)    ← API 1회 소모
[I2861][전략A] 변동 없음: total_count=...   ← API 1회 소모
```

**Pass 조건:**
- 30분 주기 1회 실행 시 API 호출 카운트가 `1~3회` 이내로 확인
- 대시보드 설정 탭 → "API 사용 현황"에서 오늘 사용량이 1~3회씩 증가하는 것을 확인

---

### 테스트 시나리오 2: 소량 변동 — 정확도 검증 (가장 중요)

**목적:** diff_count = 1~5 수준의 실제 변동이 발생했을 때 누락 없이 감지되는지 확인

**실행 방법 (사용자/개발자 공동):**
1. 식품안전나라 홈페이지(foodsafetykorea.go.kr)에서 임의의 업소 인허가 변경 내역을 직접 확인
2. 30분 후 ApprovalRadar 대시보드에서 해당 업소가 신규 또는 변경 건으로 표시되는지 확인

**기대 로그 패턴:**
```
[I2859][전략B] Ping: N건 신규 감지, 탐색 계속
[Delta 감지] Tail XXXXX → XXXXX+N (+N건 신규 삽입)
⚙️ 피벗 60개 Shift 오프셋 보정 시작...
📥 [구간 ...~...] 내에 N건의 중간 삽입 감지.
✅ 모든 변경분(N건)의 DB 업데이트 및 커밋 완료.
```

**Pass 조건:**
- 식품안전나라에서 확인한 변동 건이 ApprovalRadar 대시보드에 나타남
- SSE 알림(화면 상단 토스트)이 30분 이내에 수신됨
- 대시보드 새로고침 없이 자동으로 데이터가 갱신됨

---

### 테스트 시나리오 3: 장기 다운타임 복구 — API 호출 수 검증 (핵심)

**목적:** 개선 후 로직이 대량 누적 시에도 일일 API 한도 이내에서 동기화를 완료하는지 검증

**실행 방법 (개발자):**
1. 서버를 종료한 뒤 **48시간 이상** 대기 (또는 DB의 `meta_state.json`에서 `last_total_count`를 임의로 낮춰 시뮬레이션)
2. 서버를 재시작하고 첫 번째 크롤링 주기 완료까지 로그를 실시간 감시

**시뮬레이션용 빠른 검증 (수동 테스트):**
```python
# meta_state.json에서 last_total_count를 실제값 - 500으로 조작
# 예: "last_total_count": 300000 → 299500
# 이후 서버 재시작하면 diff_count = 500으로 인식하고 동작
```

**기대 로그 패턴:**
```
[I2859] 🔍 [Delta 감지] Tail 299500 → 300000 (+500건 신규 삽입)
⚙️ 피벗 60개 Shift 오프셋 보정 시작...
  [청크 스캔] p_idx=5000: 페이지 1회 호출, 메모리 탐색으로 offset=8 확정
  [청크 스캔] p_idx=10000: 페이지 1회 호출, 메모리 탐색으로 offset=15 확정
  ...
✅ 총 소요시간: X.XX초, 변경분 500건 DB 업데이트 완료.
```

**Pass 조건:**
- 로그에서 `[API 호출]` 카운트가 **100회 이내** (이론값 81회)로 확인
- `server.log`에 `API 키 잔여량 경고` 메시지가 **발생하지 않음** (900회 미만)
- 대시보드에 500건 내외의 신규 데이터가 정상 표시됨

### 테스트 시나리오 4: Circuit Breaker 발동 검증

**목적:** 극한 상황에서 Circuit Breaker가 시스템을 보호하고 ALERT SSE를 정상 발송하는지 검증

**실행 방법 (개발자):**
```python
# meta_state.json에서 last_total_count를 실제값 - 10,001로 조작
# 이후 서버 재시작
```

**기대 동작:**
1. 서버 로그: `[긴급] diff_count=10,001건 감지 → Circuit Breaker 발동, 이번 주기 ABORT`
2. 대시보드 팝업: "크롤러 긴급 중단: 변동분 10,001건 감지 — API 한도 초과 위험. 수동 조치 필요."
3. API 호출 카운트: **20회 이내** (Tail 탐색 후 즉시 Abort)

**Pass 조건:**
- 대시보드에 빨간색 `ALERT` 팝업이 표시됨
- 로그에서 `[API 호출]` 카운트가 20회 이내로 확인됨
- 다음 주기(30분 후)에도 Circuit Breaker가 유지되거나 재발동됨

### 테스트 시나리오 5: 회귀 테스트 — 탐지 결과 동일성 확인

**목적:** 리팩토링 이후 기존과 탐지 결과가 동일한지 확인 (데이터 누락 없음 보장)

**실행 방법 (개발자):**
1. 리팩토링 전 코드로 `diff_count = 50` 상황을 실행하여 감지된 `lcns_no` 목록을 파일로 저장
2. 리팩토링 후 코드로 동일한 상황을 재실행하여 결과를 비교

```bash
# 결과 비교 스크립트 예시
python3 -c "
import json
before = set(json.load(open('before_result.json')))
after = set(json.load(open('after_result.json')))
print('누락:', before - after)
print('추가:', after - before)
print('일치 여부:', before == after)
"
```

**Pass 조건:**
- `누락: set()` — 기존 로직이 찾은 데이터를 새 로직도 모두 찾음
- `추가: set()` — 의도치 않은 중복/오탐이 없음
- `일치 여부: True`

### 테스트 시나리오 6: 피벗 갱신 정확성 확인 (Phase 2 검증)

**목적:** Phase 2에서 `_fetch_page` 기반으로 생성된 피벗의 Boundary 값이 정확한지 검증

**실행 방법 (개발자):**
```bash
# meta_state.json에서 pivots 섹션 확인
cat result/meta_state.json | python3 -m json.tool | grep -A 4 '"5000"'
```

**기대 출력:**
```json
"5000": {
  "LCNS_NO": "실제 5,000번째 레코드의 인허가번호",
  "LAST_LCNS_NO": "실제 5,999번째 레코드의 인허가번호",
  "CHNG_DT": "20250101",
  "BSSH_NM": "가나다 음식점"
}
```

**Pass 조건:**
- `LCNS_NO`와 `LAST_LCNS_NO`가 모두 비어있지 않음
- API를 통해 해당 인덱스를 직접 조회하여 값이 일치하는지 수동 확인 가능
