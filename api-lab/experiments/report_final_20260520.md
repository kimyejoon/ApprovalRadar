## 1. 프로젝트 배경 및 초기 제약

### 궁극적 목표
식품안전나라 I2861 API에서 **당일 인허가 변경분을 실시간**으로 포착한다.

### 초기에 알려진 제약사항

| 제약 | 내용 |
|------|------|
| API 일일 한도 | 키 1개당 1,000건/일 |

| CHNG_DT=오늘 조회 | 저녁 19:00 이후에만 가능 |

### 실패한 전략들

- **전략 A (이진탐색)**: 데이터 Gap 존재, 피봇 기준 불안정으로 실패
- **전략 B (Full Scan)**: API 키 한도 초과 + 19:00 이전 오늘 데이터 포착 불가

## 2. 실험 1 — 정렬 기준 분석

### 실험 내용
동일 시작점(start=1), 크기만 다른 조회 + 1~5000 5페이지 경계 분석

### 발견

| 항목 | 결과 |
|------|------|
| 페이지 분할 기준 | `BSSH_NM ASC` 사전순 기반 `LIMIT/OFFSET` |
| 동일 LCNS_NO 이력 | **페이지 경계를 넘지 않음** (업소 단위 묶음) |
| size가 커질수록 | 최신 CHNG_DT 업소가 앞에 위치 |

### 추정 내부 쿼리

```sql
SELECT * FROM v_i2861
ORDER BY BSSH_NM ASC, CHNG_DT DESC
LIMIT :size OFFSET :start
```

- `v_i2861`은 BSSH_NM 기준으로 미리 정렬된 View (또는 인덱스)
- BSSH_NM이 동일한 LCNS_NO 그룹은 CHNG_DT DESC로 내부 정렬

## 3. 실험 2 — CHNG_DT 파라미터 비교

### 실험 내용
`1/5000` plain vs `1/5000/CHNG_DT=20260520` 5000건 비교

### 발견 (최종 수정)

> **이전 보고에서 오류 수정**: ERR 페이지는 네트워크 일시 오류였음.  
> 실제 두 데이터셋은 **99.9% 동일**, 차이는 오늘 날짜 5건뿐.

| 항목 | Plain 5000건 | CHNG_DT=오늘 5000건 |
|------|------------|-------------------|
| 고유 LCNS_NO | 1,647개 | 1,653개 |
| 교집합 | 1,645개 (99.9%) | ← |
| 오늘(20260520) 레코드 | **0건** | **5건** |
| CHNG_DT 분포 | 어제까지 동일 | 어제까지 동일 |

## 4. 실험 3 — total_count 공식 규명

### 수집 데이터 (View A 기준, 3개 앵커 모두 동일)

| size | total_count | tc/size |
|------|------------|---------|
| 1 | 8 | 8.00 |
| 2 | 14 | 7.00 |
| 5 | 26 | 5.20 |
| 10 | 38 | 3.80 |
| 20 | 82 | 4.10 |
| 50 | 175 | 3.50 |
| 100 | 298 | 2.98 |
| 200 | 844 | 4.22 |
| 300 | 1,373 | 4.58 |
| 500 | 2,573 | 5.15 |
| 700 | 2,810 | 4.01 |
| **1000** | **1,307** | **1.31 ← 급락** |

### 핵심 결론

1. **위치(startIdx) 완전 무관** — anchor=1, 400001, 800001 모두 동일
2. **size=1000에서만 급락** (2810→1307): 비단조(non-monotone) 함수
3. **신규 삽입 감지에 사용 불가** (고정 룩업 패턴)
4. size < 1000: 근사 공식 `tc ≈ 7.33 × size^0.788` (R²=0.965)
5. **size=1000에서만 실제 COUNT(\*) 쿼리 수행** (View별로 다른 값 반환)

## 5. 실험 4 — 6번째 URL 세그먼트 스위치 발견 🔴

### 핵심 발견

```
/api/KEY/I2861/json/START/END           → View A (공식 발행본)
/api/KEY/I2861/json/START/END/[param]   → View B (라이브 DB)
```

**6번째 URL 세그먼트의 존재 여부가 완전히 다른 데이터셋을 반환한다.**

### 스위치 발동 조건 (정밀 분석)

| 6번째 세그먼트 형식 | tc (size=1000) | 건수 | View |
|---|---|---|---|
| (없음) | 1,307 | 1,000 | **View A** — 공식 발행본 |
| `CHNG_DT=20260520` (오늘) | 4,432 | 1,000 | **View B** + 날짜 기준 |
| `CHNG_DT=20260519` (어제) | 4,414 | 1,000 | **View A와 동일 데이터** |
| `CHNG_DT=20260518` (그제 이하) | 4,432 | 1,000 | **View B** |
| `aa=2` (쓰레기 KEY=VALUE) | 4,870 | 1,000 | **View B 전체** |
| `z=z`, `CHNG_DT=abc` | 4,870 | 1,000 | **View B 전체** |
| `CHNG_DT=99991231` (미래) | 4,870 | 1,000 | **View B 전체** |
| `CHNG_DT=` (빈값) | 0 | 0 | ❌ 파싱 실패 |
| `x`, `abc`, `1`, `!@#$` (=없음) | 0 | 0 | ❌ 파싱 실패 |

### 파싱 규칙

```
조건 1: 6번째 세그먼트에 '=' 포함 + 값이 비어있지 않음 → View B 발동
조건 2: 값이 CHNG_DT이고 유효한 날짜 형식 → 날짜 필터 적용 시도
조건 3: 그 외 모든 KEY=VALUE → WHERE 절 없이 View B 전체 반환 (취약점)
```

### 추정 서버 라우터 코드

```python
if len(segments) == 5:                   # 6번째 없음
    return query(view_A)                  # 공식 발행본

elif len(segments) == 6:
    param = segments[5]
    if '=' in param and param.split('=')[1]:    # KEY=VALUE 형식
        key, val = param.split('=', 1)
        if key == 'CHNG_DT' and is_valid_date(val):
            if val == PUBLISHED_DATE:            # 발행일(어제)이면
                return query(view_A_counted)     # 발행본 (tc만 다름)
            else:
                return query(view_B, CHNG_DT=val) # 라이브 DB
        else:
            return query(view_B)                 # ← 취약점! 필터 없음
    else:
        return error()                           # = 없으면 파싱 오류
```

## 6. 실험 5 — View A / View B 심층 비교

### 결론: 두 View는 동일한 기반 데이터

| 검증 항목 | 결과 |
|--------|------|
| 업종(INDUTY_CD_NM) 분포 | 동일 (둘 다 일반음식점만) |
| CHNG_DT 분포 (과거 날짜) | 99%+ 동일 |
| LCNS_NO 교집합 | 1,645/1,647 (99.9%) |
| 동일 LCNS_NO 데이터 | 10/10 완전 일치 |
| tc (size < 1000) | **View A = View B** 완전 동일 |
| tc (size = 1000) | View A=1,307 vs View B=4,870 **← 여기만 다름** |

### tc(1000) 차이의 의미

```
tc(size=1000)은 size=1000일 때만 실제 COUNT(*) 수행
  View A COUNT(*) = 1,307  (WHERE CHNG_DT != today 적용)
  View B COUNT(*) = 4,870  (전체, 필터 없음)

size < 1000은 동일한 근사 공식 → View 무관하게 같은 값
```

## 7. 실험 6 — CHNG_DT 날짜별 패턴 (최종 핵심 발견)

### 전체 날짜 스펙트럼 테스트

```
(plain)    tc=1,307  첫레코드=닥터로빈   CHNG_DT=20260519
──────────────────────────────────────────────────────
20260521   tc=4,432  첫레코드=(더이케이)  CHNG_DT=20260520  ← 미래!
20260520   tc=4,432  첫레코드=(더이케이)  CHNG_DT=20260520
20260519   tc=4,414  첫레코드=닥터로빈   CHNG_DT=20260519  ← 어제만 특별!
20260518   tc=4,432  첫레코드=(더이케이)  CHNG_DT=20260520
20260517   tc=4,432  (동일)
  ...
20000101   tc=4,432  (동일)              ← 26년 전 날짜도!
──────────────────────────────────────────────────────
(aa=2)     tc=4,870  첫레코드=(더이케이)  CHNG_DT=20260520
```

### 해석: "발행일(Publication Date)" 모델

**오직 CHNG_DT=어제(20260519)만 다르다** → 어제가 "가장 최근 공식 발행일"이기 때문.

```
서버 데이터 구조:
  [공식 발행본] = 매일 갱신되는 스냅샷 (현재 기준: 20260519)
                 plain 조회 = 이 발행본 반환
                 CHNG_DT=발행일 조회 = 이 발행본 반환 (tc만 다름)

  [라이브 DB]   = 실시간 변경분 포함 (오늘 20260520 데이터)
                 CHNG_DT=발행일 외 모든 값 = 라이브 DB 반환
```

| 서비스 | 동작 |
|--------|------|
| I2861 | 오늘 데이터 **침묵 필터링** (에러 없이 제거) |
| I1200 | CHNG_DT=오늘 → INFO-700 **명시적 차단** |

**I2861은 다른 서비스와 완전히 다른 구현** — 오래된 코드이거나 다른 개발자 작성. 이것이 취약점이 I2861에만 존재하는 이유.

## 10. 핵심 전략 도출 — 궁극적 목표 달성 방법

### ✅ 발견된 우회 방법

```
실시간 오늘 데이터 접근 URL:
GET /api/KEY/I2861/json/1/1000/CHNG_DT=20000101

또는 (더 많은 데이터):
GET /api/KEY/I2861/json/1/1000/aa=2
```

**CHNG_DT=발행일(어제) 값만 피하면 언제든지 오늘 데이터 접근 가능.**

### 폴링 전략 비교

| 방식 | URL | tc | 오늘 데이터 | 하루 API 소모 |
|------|-----|----|-----------|-------------|
| 기존 plain | `/json/1/1000` | 1,307 | ❌ | 288회(5분) |
| CHNG_DT=오늘 | `/json/1/1000/CHNG_DT=오늘` | 4,432 | ✅ | 288회 |
| **쓰레기 파라미터** | **`/json/1/1000/aa=2`** | **4,870** | **✅** | **288회** |
| CHNG_DT=과거 | `/json/1/1000/CHNG_DT=20000101` | 4,432 | ✅ | 288회 |

### 권장 폴링 로직

```python
# 실시간 변경 감지 (5분 주기)
BASE = "http://openapi.foodsafetykorea.go.kr/api/{KEY}/I2861/json/1/1000"
POLL_URL = BASE + "/CHNG_DT=20000101"  # 또는 /aa=2

# 1회 폴링: 1000건 조회
# 오늘 날짜(CHNG_DT=today) 레코드만 추출 → 신규 변경분

# 하루 API 소모:
# 5분 × 12회/시 × 24시 = 288회 → 712회 여유분으로 상세 조회 가능
```

### 감지 방법

```python
# 직전 폴링 결과와 비교
prev_first_lcns = "..."

r = fetch(POLL_URL)
today_records = [row for row in r["rows"] if row["CHNG_DT"] == today]

if today_records:
    new_ones = [r for r in today_records if r["LCNS_NO"] not in known_lcns]
    if new_ones:
        alert(f"신규 변경 {len(new_ones)}건 감지!")
```

## 11-B. 신규 가설 — "발행 방식 DB + CHNG_DT = 발행일 셀렉터"

> 제안 시각: 2026-05-20 23:30 | 상태: **미검증, 검증 예정**

### 핵심 아이디어

기존에 "CHNG_DT로 날짜를 필터링한다"고 이해했으나,  
**CHNG_DT는 어느 발행본(Publication Snapshot)을 볼 것인지 선택하는 셀렉터**일 가능성.

```
[식품안전나라 서버 추정 내부 구조]

  live_db (실시간 트랜잭션 DB)
      ↓ 매일 19:00~19:30 배치 작업 (이 시간 응답 200초+ 관측)
  publication_YYYYMMDD (일별 동결 스냅샷)

API 라우팅 추정:
  CHNG_DT 없음           → publication_최신  (현재: 20260519)
  CHNG_DT=20260519       → publication_20260519  ← 최신 발행본 (어제)
  CHNG_DT=20260518       → publication_20260518  → 없음 → live_db fallback
  CHNG_DT=20260521(미래)  → publication_20260521  → 없음 → live_db fallback
  CHNG_DT=20000101(먼과거)→ publication_20000101  → 없음 → live_db fallback
  aa=2 (쓰레기)           → 매핑 없음 → live_db fallback
```

### 모든 관측값 설명력 비교

| 관측값 | 기존 "필터" 가설 | "발행 방식" 가설 |
|--------|--------------|----------------|
| plain = CHNG_DT=어제 동일 첫레코드 | ❓ 설명 어색 | ✅ 둘 다 최신 발행본 |
| CHNG_DT=그제 → 오늘 데이터 노출 | ❓ 왜 그제가 오늘을? | ✅ 그제 발행본 없음 → live_db |
| CHNG_DT=미래(20260521) → 오늘 데이터 | ❓ 이상함 | ✅ 미래 발행본 없음 → live_db |
| CHNG_DT=20000101 → 오늘 데이터 | ❓ 완전히 이상함 | ✅ 26년 전 발행본 없음 → live_db |
| 17~19시 응답 200초 이상 | ❓ 불명 | ✅ 19:00 발행 배치 작업으로 인한 부하 |
| 19:00 이후에도 plain = 어제 유지 | ❓ 왜 갱신 안 되나? | ✅ 오늘 것은 내일 발행 예정 |

### tc 차이도 이 가설로 설명

```
tc(plain, 1000)           = 1,307  ← 최신 publication의 COUNT(*)
tc(CHNG_DT=어제, 1000)    = 4,414  ← 동일 publication (다른 쿼리 경로)
tc(CHNG_DT=그외, 1000)    = 4,432  ← live_db COUNT(*)
tc(aa=2, 1000)            = 4,870  ← live_db 전체 COUNT(*) (추가 필터 없음)
```

### 19:00 제한의 재해석

```
"오늘날짜에 생성 및 변경된 데이터는 19시 이후에 호출이 가능합니다."
  ↑ 이 메시지는 CHNG_DT=오늘 를 정상 경로로 조회할 때만 발동
  
live_db fallback(aa=2, CHNG_DT=그제 등)은 이 체크를 통과하지 않음
  → 19:00 제한이 발행 시스템의 "공식 경로"에만 적용되는 버그/설계 결함
```
